# Multi-Sensor Heating — requirements baseline

This is a **description of the behavior implemented in this repository**, not a proposal for unimplemented features. Use the IDs below when requesting changes: edit the requirement and its acceptance criteria first, then change code and tests. `F` denotes functional behavior; `N` denotes a non-functional constraint. Defaults and limits are part of the baseline unless explicitly revised. See [README.md](README.md) for installation and user instructions.

## Scope and terms

- One Home Assistant (HA) config entry represents one room and controls one `climate` radiator thermostat (TRV). Multiple rooms are supported; a TRV can belong to only one room. Control is local through HA entities and services, not a separate cloud or scheduling service.
- **Room target** is the desired reference-room temperature. **Effective target** is a per-sensor target derived from it. **Heating demand** is a decision to ask the TRV to heat, not a measurement of its actual valve position.
- The TRV's own temperature is always a member of the room's temperature-sensor set. Other sensors, window/door contacts and a child-lock entity are optional. The **reference sensor** is used for the displayed room temperature, offset statistics and first-priority control decisions; the other sensors still participate in control.
- The requirements describe the current implementation as of this document. Behavior that is ambiguous or not implemented is listed under **Decisions needed**, rather than silently treated as a promise.

### Control inputs and decision rules

| ID | Requirement / acceptance criterion | Implementation / evidence |
| --- | --- | --- |
| F-04 | Room control shall use the TRV temperature plus every configured temperature sensor with a valid, non-stale reading. `unknown`, `unavailable`, missing/non-numeric or stale readings are excluded; staleness is measured against HA `last_reported` and defaults to **120 min**. The reference temperature may be unavailable while another sensor still controls the room. | [coordinator](custom_components/multisensor_heating/coordinator.py), [recorder helpers](custom_components/multisensor_heating/recorder_util.py), [tests](tests/test_review.py) |
| F-05 | For each sensor, with room target `T`, offset `o`, hysteresis `h`, minimum `m` and maximum `M`: `effective_target = clamp(T + o, m + h/2, M - h/2)`; if that clamp interval is inverted, both bounds are replaced by `(m + M)/2`. A valid reading `< m` is `below_min`; `> M` is `above_max`; otherwise `>= effective_target + h/2` is `hot`, `<= effective_target - h/2` is `cold`, and the remainder is `ok`. Missing readings are `unavailable`. Equality with a safety bound is not a safety breach. | [controller](custom_components/multisensor_heating/controller.py), [unit tests](tests/test_controller.py) |
| F-06 | In normal Heat control, evaluate **the configured reference sensor first**, then all additional sensors. A reference `below_min`/`cold` heats (`below_min`/`heating`), even if an additional sensor is above max; a reference `above_max` stops (`above_max`), even if an additional sensor is below min/cold. If the reference does not decide (including when unavailable), **any additional `above_max` stops** before any additional `below_min`/`cold` heats. Thus with two additional sensors, above-max wins over cold or below-min regardless of their order. If no rule decides, all available sensors `hot` → idle; otherwise retain the previous heating state only if the previous reason was normal sensor control, else idle. A reference `hot` or `ok` is not by itself a stop command. The deficit remains the maximum `effective_target - reading` over available sensors and may be negative. | [controller](custom_components/multisensor_heating/controller.py), [unit tests](tests/test_controller.py) |
| F-07 | When heating, the requested setpoint shall be `clamp(ceil_to_0.5(TRV_temperature + max(min_boost, gain × deficit)), min_setpoint, max_setpoint)`. When not heating, it shall normally be `clamp(floor_to_0.5(TRV_temperature - stop_margin), min_setpoint, max_setpoint)`. Defaults: room target **21 °C**, offset **0 °C**, sensor min/max **5/30 °C**, gain **2**, hysteresis **0.5 °C**, min boost **1 °C**, stop margin **2 °C**, TRV limits **5/30 °C**. | [controller](custom_components/multisensor_heating/controller.py), [constants](custom_components/multisensor_heating/const.py), [unit tests](tests/test_controller.py) |
| F-08 | The decision precedence shall be: automation Disabled → TRV unavailable → window blocked **or recovering** → room Off → Vacation → normal Heat control (including no-temperature-data fallback). Disabled or unavailable shall send no TRV action. Window blocked, recovery and Off shall hold the minimum TRV setpoint in heat/Permanent Hold; Vacation shall hold the clamped vacation temperature (default **10 °C**). These modes override per-sensor safety ranges. | [controller](custom_components/multisensor_heating/controller.py), [mode tests](tests/test_mode.py) |
| F-09 | An `on` window/door shall block heating after the configured open delay (default **120 s**), measured from the **first opening in a continuous room-wide interval**: overlapping contacts count as one opening ending when the last contact closes. On closure, if aggregate open duration `d < 60 s`, resume normal control (unless an earlier recovery period remains); if `60 ≤ d ≤ 1800 s`, hold minimum setpoint for `300 + (d - 60) × 900/1740` seconds after the last closure; if `d > 1800 s`, hold it for **1200 s**. Thus 1 minute open gives 5 minutes recovery and 30 minutes or more gives 20 minutes. A new opening during recovery does not shorten the existing recovery deadline; after it closes, use the later deadline. Evaluate at open-delay and recovery deadlines. Persist an active recovery deadline across restarts; an open contact that was blocking before restart stays blocked while open. A distinct `window_recovery` reason and `window_blocked` binary-sensor state shall expose the recovery period. | [coordinator](custom_components/multisensor_heating/coordinator.py), [controller](custom_components/multisensor_heating/controller.py), [tests](tests/test_controller.py), [tests](tests/test_init.py), [regressions](tests/test_review.py) |
| F-10 | If the TRV entity is available but **all sensor readings are unavailable OR its own current temperature is unavailable**, the reason shall be `no_sensors`, demand false, and the requested setpoint the room target rounded down to 0.5 °C and clamped to TRV limits. Raise a HA Repairs warning while this condition holds and clear it when resolved. In this fallback, a manually `off` TRV is not deliberately switched back to heat. | [controller](custom_components/multisensor_heating/controller.py), [coordinator](custom_components/multisensor_heating/coordinator.py), [unit tests](tests/test_controller.py), [regressions](tests/test_review.py) |
| F-21 | **Opportunistic heating.** All loaded rooms are assumed to share one heat source. A room has **primary demand** when F-06 makes it heat on its own sensors (reason `heating` or `below_min`). While at least one *other* room has primary demand, a room that F-06 would leave `idle` shall heat with reason `opportunistic` if its reference reading is valid and below its effective target. It shall use the normal F-07 heating curve. Once started, opportunistic heating follows the normal stop rules: it continues through the dead band and ends when every available sensor is `hot`, any F-06 stop rule (`above_max`) applies, or F-08 takes precedence (Disabled, TRV unavailable, window open/recovery, Off, Vacation, no data). It also ends as soon as no other room has primary demand; it then does **not** continue through the dead band. Opportunistic heating never counts as primary demand, so it cannot trigger other rooms. When a room's primary demand starts or stops, or the room unloads, other rooms are re-evaluated promptly. | [controller](custom_components/multisensor_heating/controller.py), [coordinator](custom_components/multisensor_heating/coordinator.py), [unit tests](tests/test_controller.py), [integration tests](tests/test_opportunistic.py) |

### TRV actuation and user controls

| ID | Requirement / acceptance criterion | Implementation / evidence |
| --- | --- | --- |
| F-11 | While controlled, a TRV exposing the `Permanent Hold` preset shall be brought to that preset; other TRVs shall be brought to HVAC `heat`. Off and window-blocked modes shall **not** send HVAC `off` or a TRV `Off` preset; instead they use the minimum setpoint. Disabled shall stop enforcement without sending a TRV command. When control is active, externally changed mode/preset is corrected on later evaluations; setpoint changes are corrected only when the current value does not satisfy the tolerance/idle rules in F-12. | [coordinator](custom_components/multisensor_heating/coordinator.py), [controller](custom_components/multisensor_heating/controller.py), [preset tests](tests/test_presets.py), [mode tests](tests/test_mode.py) |
| F-12 | TRV setpoint calls shall be skipped when the requested value equals the reported value. Changes of reason/heating state bypass the normal minimum write interval (default **180 s**); otherwise that interval applies. During continued heating, an existing setpoint within **0.5 °C** of the ideal is retained; when idle, a setpoint already at least **0.5 °C** below the TRV temperature is retained. HVAC-mode corrections are throttled to **60 s** while waiting for gateway confirmation; failed setpoint service calls are eligible for retry after about **60 s**. Service failures are logged and must not stop evaluation. | [controller](custom_components/multisensor_heating/controller.py), [coordinator](custom_components/multisensor_heating/coordinator.py), [unit tests](tests/test_controller.py), [regressions](tests/test_review.py) |
| F-13 | Users shall be able to choose `heat`, `vacation`, `off`, `disabled` using a per-room select; a room climate entity shall expose a 5–30 °C target at 0.5 °C steps, Heat/Off and None/Away preset; an automation switch shall toggle control. Changes through any of these controls shall update the same room state. `disabled` takes precedence when deriving the displayed room mode. | [select](custom_components/multisensor_heating/select.py), [climate](custom_components/multisensor_heating/climate.py), [switch](custom_components/multisensor_heating/switch.py), [tests](tests/test_mode.py) |
| F-14 | Each sensor (including the TRV) shall have offset (`-10..10`, step `0.1` °C), minimum (`5..30`, step `0.5` °C), and maximum (`10..35`, step `0.5` °C) number entities. Room-level numbers shall expose gain (`0.5..10`, step `0.1`), hysteresis (`0.1..3` °C, step `0.1`), and vacation temperature (`5..20` °C, step `0.5`). Attempts to set a sensor minimum above its maximum or maximum below its minimum via these entities are rejected. | [numbers](custom_components/multisensor_heating/number.py), [regressions](tests/test_review.py) |
| F-15 | If a lock entity is configured, a switch shall optionally enforce its locked state. When enabled, an observed `unlocked` state triggers `lock.lock`, no more often than once per **60 s**; turning the switch off issues `lock.unlock`. Disabling room automation suspends automatic lock enforcement. | [switch](custom_components/multisensor_heating/switch.py), [coordinator](custom_components/multisensor_heating/coordinator.py), [tests](tests/test_init.py) |

| F-16 | Each room shall publish a device and non-polled entities: room climate (reference reading, target, HVAC action, reason, sensor statuses), mode select, automation switch, optional lock switch, heating and window-blocked binary sensors, control-reason/deficit/requested-setpoint sensors, per-sensor effective-target sensors and numbers. Per-sensor status values are `below_min`, `cold`, `ok`, `hot`, `above_max`, `unavailable`; control reasons are those in `const.REASONS`. ## Decisions needed before changing the baseline

These are **not requirements yet**. Agree on intended behavior and add acceptance tests before promoting them.

1. **No-data fallback:** F-10 also triggers when the TRV's own temperature is missing, even if another sensor is valid. Is holding the room target then preferable to controlling from the remaining sensors? Should a manually-off TRV receive even a setpoint update?
2. **Window contacts:** Missing/unknown contacts are treated as closed, and chart “window” bands show *blocked or recovering*, not raw open periods. Should either behavior change?
3. **Configuration validity:** Per-sensor min ≤ max is checked at the number-entity boundary, not when restoring previously stored values. Config-flow TRV min/max are independently selected. Should cross-field validation be guaranteed at every ingress?
4. **API permissions and scale:** Are ordinary authenticated websocket clients intended to read all room metadata/history? Should history point count or room count be bounded beyond the existing hours limit?
5. **Frontend refresh/navigation:** Cards fetch room metadata initially (and history periodically); dashboard strategy paths derive from room-name slugs. Define expected behavior for renames, duplicate slugs and rooms added while a dashboard remains open.
6. **Deployment targets/localization:** The HACS minimum HA version is `2025.1.0`, while the documented test harness is HA `2026.10`; the dashboard's text is mostly hard-coded English. Specify minimum *verified* HA version and desired translation/accessibility coverage before imposing compatibility or localization guarantees.
